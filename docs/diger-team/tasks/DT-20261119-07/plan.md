## Design (smallest change the file already supports)
WHERE THE LABEL GOES: the file's contact column has ONE status column next to it (`status_key`, «حالة التوثيق»; only the phone has a type column). No new column (it would change the plan and the card). The label goes in the STATUS cell after the verdict, with the em dash the repo already uses: `«غير موثّق — إيميل شخصي»`. Helpers in src/lib/agentMission/emailVerification.ts (pure): constants `EMAIL_LABEL_PERSONAL_AR = "إيميل شخصي"`, `EMAIL_LABEL_COMPANY_AR = "إيميل الشركة"`, `EMAIL_LABEL_SHARED_AR = "مشترك"`; `labelledStatus(status, label)` = `label` when status is empty, the status unchanged when it already contains the label, else `` `${status} — ${label}` ``; `statusHead(s)` = the text before the first « — » (the verdict).
(a) PERSONAL MAILBOX (D2): kept as `keptPersonal` (the first one, with its finder and call id); the chain CONTINUES for a work address. After the chain: a work address found → it fills the cell (status = its verdict); the personal one is kept IN THE ROW TOO, in the same status cell as a note «— إيميل شخصي: {address}» (the simplest the file supports: no new column; a second column is a follow-up decision); no work address → the personal one fills the cell, status «{verdict} — إيميل شخصي».
(b) COMPANY'S OWN ADDRESS (D1, D3): kept as `keptCompany` (given by the source or returned by a finder); the chain continues for a personal work address; none found → the company address fills the cell, status «{verdict} — إيميل الشركة». When a better address replaces it nothing is lost (the company row already holds that address). Precedence of the cell when nothing better is found: personal mailbox over company address (the customer asked for the PERSON's address).
(c) SHARED ADDRESS (D4): `finish()` no longer clears: every holder keeps the address and its status gets « — مشترك » (`labelledStatus(thatRow's status, EMAIL_LABEL_SHARED_AR)`); `found` is no longer decreased.
A kept value is a delivered value: it counts for «وُجد لـ N من M» (found += 1), the attempts file records outcome `value`, the verifier still only labels it (unchanged), the person-email learned for the phone step is NOT fed with a personal or company address (as before: only a work address).
L1/2 ALTERNATES AFTER AN EMPTY CHAIN: the loop's limit becomes `maxTries + FINDERS_PER_STEP` attempts (`const maxTotal = maxTries + FINDERS_PER_STEP`; the chain list is `finders` then `alternates`, so the extra attempts can only be alternates). Every attempt still passes `affordable(finder)` (the per-person ceiling = the chain's own price), `attempt()` (the step cap, the job budget, the time limit) and the same stop rules. A hit ends the loop; no alternate is asked after a hit. The e-mail step gets alternates like the phone step: `contactFinders.ts` line 280 `kind === "phone" && help.alternates…` → both kinds; `tools.ts` `contactAids` (email branch) adds `alternates: alternateFinderSourcesOf("email", ctx.catalog, allowedHelper, ctx.stats)`; `b2bPlanning.ts:32` (the stage-3 planner; flag-gated) is NOT changed in this PR (its e-mail steps keep today's chain).
ITEM 3 (hit only with a value): already true in contacts.ts: `hit = foundContactIn(...)` is null for an object with null fields, the outcome is `empty`, `found` counts hits only, the line and the attempts file follow. This PR PINS it with tests. What still counts SHAPES as rows is the gateway's `rows_returned` (gateway.ts:396-398, §7) and the finder RANKING that reads it (sourceRanking.ts:91): changing it needs Megz's approval for gateway.ts or a ranking-side rule; reported, not done here.
