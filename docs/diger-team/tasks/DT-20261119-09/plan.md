## Problem (code, at 7e8cc484)
1. The cap we send in `X-Treg-Route-Max-Cost` is `Number(Math.max(estimate, 0.001).toFixed(6))` (src/lib/server/spendGate/bounds.ts, `tregRouteCapUsd`; the same formula in agent/src/gateway.ts `tregRouteMaxUsd`). `toFixed(6)` rounds half to nearest: aiark.people.search (catalog price 0.0026335) is sent as 0.002633, one micro-dollar UNDER its price. TREG's doc (https://treg.to/integrate.md): "If the reserve would exceed it treg answers 402 `route_max_cost` with `max_cost_micro` and `estimated_cost_micro`". Computed over the 2,741 priced endpoints of data/treg/treg_catalog_sellable.json: 3 have a cap below their price: aiark.people.search, aiark.people.enrich, oceanio.people.phone.reveal. The earlier live incident of 2026-10-31 15:50 (one 402 on `aiark.people.search` with a 6.64 USD balance) fits the same cause.
2. src/functions/shared/tregClient.ts reads a 402 as a price cap only when the TOP-LEVEL `responseBody.error === "route_max_cost"`; every other 402 is `isPlatformBalanceLow`. Live the stored text began with `{` (the fields were not in a top-level error string), so six price caps were read as «balance low»: the key pool ran its free identity + balance reads (tregKeyPool.ts `balance402`), found the balance healthy → `paymentScope = "endpoint"` → trace «endpoint_payment_refused» (gateway.ts) → `classifyFailure` (sourceRanking.ts) = `payment` → blitzapi/aiark demoted in later rankings.

## Changes (5 source files + 4 test files; one concern: the cap and its refusal)
1. src/lib/server/spendGate/bounds.ts: NEW `ceilToMicroUsd(usd)` (round UP to the micro-dollar; float noise below 1e-6 micro is not a fraction: an exact price stays exact); `tregRouteCapUsd(estimate) = ceilToMicroUsd(max(estimate, 0.001))`.
2. agent/src/gateway.ts: `tregRouteMaxUsd` returns `tregRouteCapUsd(estimateCallUsd(...))` (the same number the call sends; line 303 already uses `tregRouteCapUsd`); the trace text of a price-cap refusal is prefixed `route_max_cost: ` (the endpoint-scope prefix stays for a real endpoint refusal); comment updated.
3. src/functions/shared/tregClient.ts: NEW exported `isRouteMaxCostBody(body)` (structure, no word list). Order of the rule (فزاع pre-push, P0): (1) an explicit code other than `route_max_cost` (`insufficient_balance`, `payment_required`, …) ALWAYS wins: not a price cap, whatever fields travel with it, so the key pool still checks the key and recovers on a funded standby; (2) the code `route_max_cost` (top level, in a `detail`/`error` object, or in a JSON string under `detail`/`error`, which is a CONTAINER and never itself a code) is a price cap; (3) no code at all: `estimated_cost_micro` with `max_cost_micro` is a cap only when the reserve is ABOVE the cap; `estimated_cost_micro` alone (the shape seen live) is a cap; `max_cost_micro` alone is not. `isRouteMaxCost`/`isPlatformBalanceLow` use it; the result `error` is `route_max_cost` for a detail-wrapped cap.
4. agent/src/gateway.ts writes a trusted `_failure_kind` with the failed call (`price_cap` when the client classified a price cap, `endpoint_payment` when the key pool found an endpoint-scope payment refusal); src/lib/agentMission/sourceRanking.ts `classifyFailure` trusts it: `price_cap` → `none`, `endpoint_payment` → `payment` (the demotion stays, whatever cost fields the clipped text carries). Only a row recorded BEFORE the fix (no kind) falls back to the text: `endpoint_payment_refused` with the clipped cap fields (`route_max_cost`, `max_cost_mi…`, `estimated_cost_mi…`) is a price cap that was mislabelled → `none`.
5. tests/helpers/tregPoolKit.ts: two fake modes `route_cap_detail`, `route_cap_fields` (the observed shape); tests/phase5-stage-cap.test.ts: add `aiark.people.search` to the ids whose sent cap equals the bound; tests/agent-stuck-mission-fix.test.ts: one case (trace `route_max_cost: `, health `none`); NEW tests/dt-0119-09-route-cap.test.ts (property over the catalog, exact-micro counters, structure table, client + key pool, source health).
