Generated by `npx tsx scripts/capacity/report.ts` from `docs/capacity/cpu-measurements.json` (measured by `tests/cpu-measure-routes.test.ts` and `tests/cpu-measure-worker.test.ts`) and `scripts/capacity/cpuModel.ts`. A test fails if this file differs from that output.

A handler needs 0.05 to 25 ms; the observed average of 0.108 s per invocation is therefore almost all per-invocation overhead (framework, sign-in check, database client, cold starts). The one heavy item is a delivered PDF (about 430 ms raw) and Excel (about 170 ms raw).

## 2. Model

`cost(invocation) = overhead + raw_ms x speed / 1000`. The overhead is fitted so that the pre-change mix of one visitor session averages exactly 0.108 s. Two parameter sets:

| Set | speed (hosting CPU slower than the build machine) | overhead per invocation | cold starts x seconds |
|---|---|---|---|
| base | x2 | 0.1059 s (fitted) | 150 x 0.8 |
| stress | x6 | 0.150 s | 300 x 1 |

Decision rule (brief): under 2 CPU-hours expected on Saturday stay on the plan (`stay`); 2 to 3 stay with reduced invocations and hourly monitoring (`reduce`); above 3 recommend a higher plan before Saturday (`upgrade`). It is applied to the stress figure.

## 6. What the model does not know

- The real invocation mix of the plan (only 2 requests were in the last hour of runtime logs when this was written: the real average has never been measured under conference traffic).
- Whether the hosting CPU runs our handler code 2x or 6x slower than the build machine (both are shown).
- Next.js navigation requests, prefetches and the cron watchdog (a few hundred invocations, not modelled).
- Cold starts depend on how many instances the platform starts for 500 phones.
- Hourly check on the day: Vercel > Usage > Active CPU. If the day's total passes 2 hours before 14:00, set `DEGRADED_MODE=on`; at 3 hours set `DEGRADED_MODE=closed` (no new missions start; chats and plans keep working).
