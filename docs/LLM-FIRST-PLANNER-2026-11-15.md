# LLM-first planner (15 Nov 2026)

Owner direction: the model must understand the request and call the catalog's tools the way the customer wants. No word rules and no filters. Test on every platform, not only X.

## Root cause

The model never planned a social request.
- **Worker.** `agent/src/runMission.ts` sent TikTok, X, Instagram, Facebook and YouTube to a code compiler (`foundation/compilePlan.ts`) that re-read the Arabic request with regular expressions (`buildAsk`, `buildRequestContract`). It used 12 hand-written tool cards out of 3,276 catalog endpoints. Every other platform got a clarifying card or was refused: `platformQuestion.ts` `OTHER_PLATFORM` covers Reddit, LinkedIn, Telegram and Threads, while the catalog has 52 Reddit endpoints alone.
- **Chat.** Its brief mode then checked the chat model's understanding against the same regex readers (`validateBrief`, the drift and requirement checks, the capability gate) and asked the customer again whenever they disagreed.
- **Effect.** Each live failure added one more rule. That is the loop.

## The fix

### Worker (`agent/src/llmPlanner/`)

It runs before every word rule, for every platform the catalog serves. Company and people research still goes to its own live-proven path.

1. **Understand.** One structured call to `claude-sonnet-5-5`. Input: the customer's own messages, today's date, and the catalog index (every platform and capability the account may use). Output: steps, each with platform, capability, parent, count, source, topic, search terms, period, language and country. Code checks only catalog names, parents and numbers, and gives its objection back to the model once.
2. **Choose.** One call per step. The step's candidate tools, described by the catalog itself (inputs, notes, paging, item fields, measured reliability, price), produce up to 3 options with exact inputs, further input sets to reach the count, and the conditions the tool cannot carry. Code drops any input the tool does not have, checks enums and required inputs, and drops a cursor from the first page.
3. **Probe.** One real first page per step through the mission's gateway, so budget, policy and recording all apply. An empty or failing option moves to the next input set, then the next option, up to 5 calls a step.
4. **Map.** One call maps the real items to columns as paths. Code keeps only paths that read a value. The item's identifiers (ids, handles, short codes, place ids, links) are kept on the row for child steps. The mapping code is generated by the existing card generator.
5. **Price.** Code computes it as the customer's count × the real rows per page × the catalog's price per call (× 1.3 for overlap between input sets), using `priceMissionByCode`.
6. **Execution.** It uses the existing engine. It pages each stage to the customer's count, then continues with the further input sets (`alternatives`); duplicates are removed. **Nothing is dropped for its meaning:** no relevance judge and no word filters. Conditions are written into the tool inputs instead, for example `from:` and `since:` on X. A condition no tool can carry is stated on the card before approval.
7. **Questions.** The model asks only when a request cannot be executed without the answer, as a question on the card. At most 2 questions are asked per mission.

### Chat (`src/lib/agentMission/chatTurn.ts`)

With the switch on, the chat skips its brief checks. A data request becomes a mission of the customer's own words. Privacy refusals, typed approval, and the open-request flows are unchanged.

### Model request

Sonnet 5.5 rejects both forced `tool_choice` and `thinking: disabled` (seen as 400s on the worker dyno). The planner uses structured outputs instead: `output_config.format` with a `json_schema` and `thinking: between_tools`. The request lives in `review.ts` (`anthropicJsonCall`), the worker's classified model path. The planner does not run while the hard spend gate is active for a mission; the gate is unset in production.

### Waiting UI

The planner writes customer progress lines (`progress` events) as it moves through the steps:
- «فهمنا طلبك: …»
- «نختار المصدر المناسب لجمع … ونجرب عينة حقيقية منه»
- «بنجهز العدد والسعر …»

The card's live line and planning steps follow them, so the card no longer sits silent for a minute.

## Switch

`agent_settings.llm_planner_v1` is ON unless set to `false`. Rollback: store `false`. The chat's brief checks and the worker's compiler then run exactly as before.

## Round 2 (16 Nov 2026): the conversation

Owner direction: when the real search finds far less than the customer asked for (4 of 400), the model does not deliver 4 and stop. It tells the customer what it found and asks what they prefer, and the answer re-plans. And the chat talks like a normal assistant.

### Scouting question (worker)

- After the first real page of a top-level step with a stated count, the planner reads the model's other input sets once each (page one only, at most 4 calls) and counts the different items. A next page anywhere means the source holds more: no question.
- If every search ended and the different items found are fewer than half of the customer's number (or nothing was found at all), the planner stops before pricing and asks. The model writes the message from code-counted facts (requested, found, searches tried); code allows only those numbers and the customer's own, and falls back to its own sentence if the model's text breaks the customer-text rules. Options: the model's (take what exists, widen by country/accounts/period/topic); the customer may also type their own.
- The answer re-plans from the whole exchange: the understanding prompt carries every question and answer. «سلّمني الموجود» sets `accepts_available` (no second question). A widening changes only the conditions the customer names.
- Limits: 2 scouting questions per mission (state in `state/llm_planner.json`, `scout: true` entries); the planner's own clarifying questions keep their limit of 2. A failed provider call is not «nothing found»: no question.
- Offline: `tests/llm-first-planner.test.ts` (SCOUTING, mission memory). Cost: up to 4 extra provider calls per short step.

### Chat

- The chat model's instructions now ask for a natural reply in the customer's dialect at the length the talk needs, without a sales pitch on every message; the reply cap is 1800 characters (was 900) and 800 tokens (was 400).
- A reply the guard refuses (Latin digit, emoji, a number the facts do not give …) is asked again once with the reasons; only a second refusal falls to the fixed text.
- While the agent's question is open (`needs_input`), a doubt about it is answered from the question's own text (its numbers are allowed), a greeting is answered naturally, and the question stays open. Tests: `tests/chat-natural-conversation.test.ts`.

Found and fixed live: (1) adding `accepts_available` as an OPTIONAL schema property made the structured-output compiler refuse the schema («Schema is too complex»): every understanding call failed for ~15 minutes after #518 and requests fell to the old path; it is REQUIRED now (#519). Any schema change must be checked against the real API before merging (the eval dyno: `agent/scripts/evalPlanner.ts`). (2) A guessed handle: the empty/unreadable first answer is now a «found 0» finding (#520, #522). (3) «Account, and widen if not enough» was planned as two steps of 400 (#521).

Open: the price of a step whose first page gave few rows is high per row (the customer pays only for what is delivered). A probe that shows a next page does not tell how many different items exist: the scouting counts only when every search ended.

## Still open

- **Facebook comments** on a page's reels: every catalog tool returned empty. This is a provider limitation, not a planning one, and the card says it before approval.
- **The X account+topic search** returns few rows per query from the provider. The precise queries found nothing more for @SaudiMOH. The only way to look further is to read the account's whole 5-year timeline and select by meaning. That is a filter, so it is the **owner's decision**; it was not built. A second tool now continues after the first tool's queries. Precision depends on the model's terms; the ambiguity rule now covers every query, and the X retest after the last PR will measure it.
- **TikTok search relevance** is the provider's: some videos returned for a topic are from the right accounts but about other things. Nothing is dropped by meaning, per the owner's decision.
