**Status:** fix implemented on branch `ccr-18c58113-f36vic` (PR below). Regression tests use recorded production evidence and make zero paid calls. **No balance, refund, price, ledger or settlement-math change was made.** The customer remediation in section 7 is a **proposal for the owner**: nothing was refunded.

400 real X posts from the **Saudi Ministry of Health's official account** about health rumors, debunking or anti-rumor work, preferably within five years.

## 3. The trace (A): request → context → interpretation → plan → query → results → validation → status

1. **Request reading** (`requestContract.ts` `sourceOf`, `topicOf`):
   * `sourceOf` reads a named source only after the words «صفحة/حساب/قناة NAME».
     * «على وزارة الصحة السعودية» (msn_93ed) was read as **no source**.
     * «الصفحة الرسمية لوزارة …» (msn_fefee) was read as `official` with no name.
   * `topicOf` stopped only at «من/في/على/…».
     * «… عبر الصفحة الرسمية … أو أي تصحيح …» became the topic (msn_fefee).
     * «الشائعات فقط» kept «فقط» (msn_dd7c).
2. **Conversation context (B)** (`chatTurn.ts`):
   * The round 57 rule («a follow-up never becomes a new mission of its own words») covers only an **open** request: planning, a question, or a plan waiting for approval.
   * `msn_fefee` had ended `unserved`, so «طيب ابحث عن الشائعات فقط» became a new mission of its four words.
   * The platform, count and account were asked again from scratch, and the original wording and the topic qualifier «الصحية» were lost. (`msn_93ed`'s three-month period was in an earlier conversation and was never carried over either.)
3. **Plan compilation (C, D)** (`compilePlan.ts`, `toolCards/x.ts`):
   * X's only verified parent card, `anyapi.x.search.posts`, has **no account input**.
   * `carriedBy` therefore counts a named source as «not carried», and `parentInputs` never wrote one.
   * The compiler still priced the plan, choosing rows by rank and marking the others as «alternatives».
   * The provider's catalog entry documents `from:` inside the query («operators like from:, since:, until: … work inline in the query»), but the compiler never used it.
4. **Provider query and results:** the queries in the table above. All three were searches across all of X.
5. **Delivery validation (I)** (`foundation/deliveryContract.ts`):
   * The contract, by its own design, **is not a filter**: «it never removes a row, never changes a value, never blocks or delays a delivery».
   * It completed the missing named-source marks (158 completions) and raised an internal admin flag.
   * Nothing carried that finding to the status or to the customer's sentence.
6. **Customer-facing status (G, H):**
   * `status = delivered > 0 ? "completed" : "unserved"`, so both deliveries were labelled `completed`.
   * The reason sentence for the recorded stop `source_exhausted` was «لأن المصدر لم يعد يعطي نتائج أخرى لهذا الطلب».
   * That sentence was false: only an incorrectly broadened query had run out, not the customer's request.

## 4. Root cause

**X had no enforceable account condition.**

* A named account on X was either not read at all, or read and then silently dropped from the query.
* The compiler priced the resulting all-of-X plan instead of refusing it.
* The customer's later turns were not carried over once a request had ended.
* At delivery, a file whose every row was marked «غير مطابق» for the named source was closed as `completed`, with a sentence claiming the customer's request was exhausted.

## 5. The fix: the AI layer understands the request; code enforces general rules on every platform

**Owner direction (14 Nov 2026):**

* Diger must not accumulate filters or rules per word, per service or per platform.
* The AI layer understands the request, asks clarifications, and Diger picks the right service and delivers what was asked.
* Code only enforces general rules that hold on every platform.

The first version of this fix (X-only account handling, Arabic word lists for institutions, follow-ups and «فقط») was **removed** and replaced by the following.

### 5.1 Understanding: the research brief (the existing AI layer) carries the source

The chat model already reads the whole conversation and writes one consolidated request («the research brief», `chat_research_brief_v1`). It merges every turn, applies corrections and asks a clarification when something is missing. It now also writes **`source`**: the account, page or channel the content must come from, as the customer wrote it.

| What | File |
|---|---|
| The prompt asks for `source`. It asks for `topic` as the subject alone, without instruction words or the source. It says a short message after a request, even one that ended, is a change of that request, and that narrowing the topic never removes the source, platform, period or count unless the customer says so. | `conversationModel.ts` |
| Code validation, general: the source must be contained in the customer's own words (**never invented**), and the consolidated request must carry it (**never dropped**). Otherwise the brief is rejected and the conversation falls back, as with every other brief rule. | `researchBrief.ts` (`source_not_written`, `source_dropped`) |

### 5.2 Enforcement: ONE source rule from the cards' own data

| Rule | File |
|---|---|
| A named source is planned only with a service that **carries** it, as the card's own data says. There are four ways: its own input (an account's or page's listing), an evidence lookup (a channel), the search's **documented operator** (X's search declares `sourceOperator: "from:"`, from the provider's catalog entry), or a search that writes the source's **name** into its query and returns the author's page (`withSource`, Facebook; rows checked by page, widening only by the customer's explicit choice). | `foundation/sourceScope.ts`, `foundation/compilePlan.ts` (`carryOf`), `toolCards/x.ts`, `toolCards/types.ts` |
| A search that carries the source by its operator checks **every row** by its own author identifier (username, author link or channel id; exact, case-insensitive). The check runs at planning and on every row the run reads (an `exact` account filter: not delivered, not charged). A display name, a fan account or «contains» never passes. | `sourceScope.ts` (`rowIsBy`), `compilePlan.ts`, `filters.ts` |
| A source no service carries with what the customer wrote is asked **once, before any price or hold**, on any platform. The options are: the identifier (when some service of the platform can take one), the explicit choice «ابحث بدون تقييد بالمصدر» (the plan then says the results are not the source's), or cancel. Never guessed. An unusable answer ends the request with nothing charged. | `agent/src/compiled.ts`, `agent/src/runMission.ts`, `agent/src/runState.ts`, `foundation/countChoice.ts` |
| `compilePlan` refuses to price an unenforced source (`source_unenforceable`). | `compilePlan.ts` |

### 5.3 General rules that stay in code (no word lists)

* **Turns:** in a revised request the latest change wins for what it names (topic, count, source, period), and everything else stays.
  * A message after the conversation's latest request **ended** that names no platform and no kind of data is planned as a change of that request.
  * This is the fallback; with the brief on, the model consolidates.
* **Numbers in words:** «آخر ثلاثة أشهر» is the same period as «آخر ٣ أشهر», using the shared number-word table.
* **Truthful outcome:**
  * «source exhausted» now reads «لأن المصدر لم يعد يعطي نتائج أخرى للبحث المعتمد في خطتك».
  * A delivery whose rows are not the named source's says so. When none is from it, it also says it is a partial delivery that does not meet the request, and the admin flag `named_source_mismatch` is raised.

**Not changed:**

* pricing, reserve, settlement math, ledger, refunds;
* the methodology purchase;
* `capability_discovery_v1`, `registry_router`, `web_via_treg` (Intelligence stays off).

## 8. Residual risks

* `from:` is the provider's documented operator, but it has not been verified by a paid call in this round. The exact per-row username check holds whatever the provider answers: a source that ignores `from:` yields fewer rows, never another account's rows.
* A revision typed **after** the account question was answered starts a new mission (round 57 rule). That mission asks the username again; it is never guessed.
* An X request that mentions an institution only as context after «في/على/من» («إضراب في جامعة القاهرة») now gets the account question. The option «ابحث في كل إكس» continues in one click.
* The edited count above the measured pool (msn_93ed: 1 found, 400 approved) is disclosed on the card, but the edit is still allowed. That is a pricing-flow decision for the owner.
