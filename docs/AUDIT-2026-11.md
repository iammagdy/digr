# AUDIT 2026-11: what each task type must deliver, and where Diger is today

Audit only. Written 2026-11-01 against `main` = `55fef0de338cd6c7d3c7af20532f072a72a6b65a`. **No product code, no SQL write, no migration, no merge of code.** Evidence = read-only SELECTs on `missions`, `mission_calls`, `mission_events` (104 missions with a `result` event, 96 with a `plan` event, 2026-10-29 to 2026-11-01, TEST account) and the code on `main` (file:line). The delivered Excel files and the raw provider pages live in storage and cannot be read by SQL: every claim about the content of a delivered file is marked NOT PROVEN unless a plan, an event or a count proves it.

Status words: **MET** (code and evidence), **PARTIAL**, **GAP**, **NOT PROVEN** (no live evidence either way). Sizes: S (under a day, no money path), M (days), L (a design decision and several parts).

## 0. Why the fixes kept reversing each other (root cause)

1. **The reference lives in people's heads and in per-incident constants.** The only generic contract in code is `src/lib/agentMission/fields.ts`: it looks at the raw page of the source and refuses a plan that drops a field CLASS the source gives (date, author, link, likes, replies, shares, views, rating, followers). It has no class for a company phone, a company e-mail, an address, a decision-maker marker, a parent title, and no notion of «what a companies delivery must contain». The model chooses the columns (`agent/prompts/system.md`), the code only checks classes. So «company e-mail and HQ phone» can never be refused, and nothing stops the next change from undoing it.
2. **Tests pin the implementation of the last incident, not the delivery.** `tests/standard-request-price.test.ts` pins the price of the standard request, `tests/people-depth-replay.test.ts` pins pages, and so on; no test asserts «a companies delivery has these columns in this order». Result: #315 moved role mailboxes out of the people rows into a company column as a by-product (`workbook.ts:141-155`, `:236`), #316 removed the mailbox lister as a people source, and nothing ever added the company e-mail as a deliverable. Likewise «verified only» (#316 item 1, empty cells) became «keep unverified with a status» (#317, #319), and the unit price of the same request went 13.33 → 13.52 → 23.77 → 24.81 → 80.73 points across #317, #319, #321 and #322 (HANDOFF figures).
3. **Planning is a model-written plan** (11,000 to 56,000 output tokens), so the shape of a delivery depends on what the model wrote that minute.

Fix direction (section 6): write the reference once as data (`taskContracts.ts`), make the plan check and the workbook builder read it, and add one golden test set that is run live after every PR.

## 1. THE REFERENCE (what a correct delivery looks like)

### A. Companies + decision makers (reference = the owner's hand-built sheet)

One table, one row per person, company cells on the first row of each company. Columns, in this order:

| # | Column | Rule |
|---|---|---|
| 1 | «م» | running number (per company group or per row, one rule, stated in the file) |
| 2 | «اسم الشركة» | tidy name (no stray separators) |
| 3 | «النشاط والتخصص» | from the source, Arabic |
| 4 | «الموقع الإلكتروني» | company domain |
| 5 | «الإيميل العام للشركة» | info@ / contact@ / sales@ on the company domain. **Top priority.** |
| 6 | «هاتف المقر الرئيسي» | **Top priority.** |
| 7 | «اسم صانع القرار» | Arabic, English in brackets |
| 8 | «المسمى الوظيفي» | Arabic, English in brackets |
| 9 | «إيميل المسؤول المباشر» | with status «موثّق» / «غير موثّق» |
| 10 | «هاتف / محمول المسؤول» | with status «موثّق» / «غير موثّق» |
| 11 | notes | e.g. «لم نجد صناع قرار في هذه الشركة» |

Rules (owner decisions): every person currently works at that company; when a company has no decision makers the count is filled with other employees (title, e-mail, mobile matter most) and the company is marked «لم نجد صناع قرار في هذه الشركة»; a found value is never dropped; unverified is shown as «غير موثّق», not emptied.

### B. Social posts (TikTok, Facebook, Instagram, X, LinkedIn, YouTube videos)
Text (or the title), date (exact, or clearly approximate with «تقريبًا»), link, account, engagement counts the source gives (likes, comments, shares, views, reposts), and every row relevant to the request (filtered in code; the reason a row was left out is in the methodology).

### C. Comments on a post or video
Comment text, author, date (exact or approximate), likes, replies; **on every row** the parent post/video link and title; zero orphan comments; the number per parent as asked.

### D. Places (maps)
Name, address, phone, rating, review count, link (Google Maps URL), one row per place; place reviews (a known place) are a separate task with text, stars, date, author, link.

### E. Cross-cutting
1. Delivered versus requested, with the truthful reason for any shortfall, computed from recorded counts.
2. Price about 10× the real cost (provider + model), computed by code (`markup` 10; 1 point = 0.10 EGP; 55 EGP per USD, so 1 USD of cost = 5,500 points; revenue in USD = points / 550). The 200-point minimum charge is the owner's own setting.
3. Planning time short enough to wait for (owner reports 5 to 7 minutes today).
4. Customer text: Arabic only, Arabic-Indic digits, no emoji, no provider name, endpoint id, USD or model vendor.
5. A follow-up message after delivery edits the delivered file (same file, new version), with a small price computed by code, and does not start a new plan.
6. Money rules unchanged: append-only ledger, deterministic ids `res_/rel_/chg_/top_`, release first, idempotent, charge = ceil(delivered × unit price) never above the reserve, 15% buffer on the reserve only, nothing spent before approval, the model never decides money, job cap 25,000 points, provider daily cap 0.80 USD.

## 3. GAPS IN DETAIL (what the reference requires / what Diger does / evidence / user impact)

### G0. No contract per task type
- **Requires:** one table «task type → required columns, sheet shape, counts».
- **Today:** `fields.ts` classes only (`FIELD_LABEL_AR` lists 10 classes; none for phone, e-mail, address, parent title). `agent/prompts/system.md` (72 lines, 35,572 bytes) tells the model what to write.
- **Evidence:** the plan columns of the last two live companies missions: `msn_7539ea17512cf58aa0e7` and `msn_4969a50fed8c45b37d8f` (section 7.3). The 1,029-line HANDOFF is the only «reference», as prose.
- **Impact:** every fix is local; the next change can reverse it (section 0).

### G1. Company official e-mail
- **Requires:** column 5 filled with the company's info@/contact@/sales@.
- **Today:** the only producer is a side effect: role/generic mailboxes the PEOPLE source returned are excluded from the people rows (`not_a_person`) and written to a company column «إيميلات عامة للشركة» when any exist (`agent/src/workbook.ts:141-155`, `:236-237`; `agent/src/runMission.ts:215-228`). #316 stopped treating the mailbox lister as a people source, and no company-level step exists: `buildContactSteps` builds steps only for people stages (`src/lib/agentMission/contactFinders.ts:181`, `stage_key: st.key` of a people stage).
- **Evidence:** the companies stage columns of `msn_7539…` and `msn_4969…` have no e-mail column (7.3). A priced source exists in the catalog: `tomba.companies.emails.list` (0.0089 USD per company: «every email address found on it»); it was called in planning only (`msn_51bd048efcfbfc5bbafc`, planning call 16:15:55, 10 rows, 0.0089 USD). The companies source itself gives `total_emails` (a count, not addresses).
- **Impact:** the owner's top-priority column is missing in every companies file.
- **Size:** M (a company-level step beside `contact_steps`, priced and capped by code the same way).

### G2. HQ phone
- **Requires:** column 6.
- **Today:** the companies source `tomba.companies.search.reveal` returns `phone_number`, `street_address`, `postal_code`, `city`, `total_emails`, `linkedin_url` and more (catalog `item_fields`, 0.000178 USD per 50 companies). The plan chose 8 columns and left the phone and address out. The company phone appears only as a fallback inside the PERSON's phone cell with the type «رقم الشركة» (HANDOFF #319 item 3).
- **Evidence:** 7.3 (columns). Fill rate of `phone_number` for Egyptian companies: NOT PROVEN (raw pages are in storage).
- **Impact:** the field is free (already paid for) and dropped.
- **Size:** S (add the class to the contract so the plan check refuses a plan that drops it).

### G3. File shape
- **Requires:** one table, one row per person, company cells on the first row, «م», notes.
- **Today:** one sheet per stage; the people sheet carries up to two parent-context columns and the link by «معرّف الأصل» (`agent/src/workbook.ts:93-137`, `MAX_PARENT_CONTEXT_COLUMNS`). Settlement counts every sheet AFTER THE FIRST minus its header row (`agent/src/finalize.ts:23` `countWorkbookSheets`; HANDOFF «FILE OUTPUT 1»: adding a sheet makes a 50-item file count 62). For the standard request the delivered count is companies + people = 5 + 10 = 15.
- **Impact:** the file does not look like the owner's sheet. A one-sheet layout changes what is counted and therefore charged (people rows only = 10, not 15), so it is a money-path decision.
- **Size:** L. **Owner decision: DECIDED in section 9** (companies + people are counted, 15 for the standard request). The layout work itself is M and belongs to PR 3; PR 1 does not change `finalize.ts` counting.

### G4. Arabic with English in brackets
- **Requires:** names and titles as «محمد سعيد (Mohamed Saied)», «الرئيس التنفيذي (CEO)».
- **Today:** cells carry the source's values. No transliteration or title lexicon in code (no match in `agent/src`, `src/lib/agentMission` for a bilingual rule); `system.md:9` says Arabic only for the model's own text.
- **Evidence:** people columns in 7.3 are single-language; titles are ranked by an English lexicon (`src/lib/agentMission/roles.ts` `titleTierOf`).
- **Size:** M. Titles by a code lexicon; names by one small batched model call per mission whose cost is added to the price by code (Haiku 5.5 is 0.10 in / 0.50 out per million tokens, `src/lib/modelPlanner/constants.ts:33`; about 25 names per call is under 0.001 USD).

### G5. Companies with no decision makers

- **Today:** four title tiers fill the count with the best of the rest (`roles.ts`, #321); the file-level sentence says how many delivered people are not decision makers and in how many companies (`decisionMakersLeftOutAr`); the result event of `msn_7539…` says «بعض الشركات عليها موظفين أقل من العدد المطلوب لكل شركة». There is no per-company marker, no notes column.

### G10. Paid comment fetches on parents with zero comments
- **Requires:** read the parent's own comment count first; do not buy a fetch for 0.
- **Today:** the engine reads every parent in order (`agent/src/engine/run.ts:128-131`); the parent's count field is used ONLY to order spare parents (`run.ts:242-243`, `CHILD_COUNT_KEY`); a spare takes over only AFTER the empty answer (`run.ts:160-165`).
- **Evidence (SQL):** 108 execution calls to `*comment*` endpoints; 9 returned 0 rows, 1 of them billed (0.00188 USD, `scrapecreators.youtube.video.comments`, status `empty`). `msn_24d0cf1d05cf5b9e9542` (YouTube): empty answers at 16:41:52, 16:42:00, 16:42:07, 16:48:15 across providers. HANDOFF #303: the TikTok source gave 0, 0, 1, 0, 10 comments for five brand-new videos. The catalog says a video with comments turned off «gives no rows».
- **Impact:** money is small (about 0.002 USD in the observed set); the cost is wasted calls, wasted time and a parent that delivers nothing.
- **Size:** S.

### G11. Single-field inputs from a parent

Recorded plans: YouTube comments bind `id → video` (11-character id only) although the parent row has the watch URL (`msn_d459af6a159abde218a9`); TikTok comments bind `id → aweme_id`.
- The `treg.*` routers take several identity keys («identity key (part of url)») and the router matches providers on the variants it was given (`src/lib/peopleSearchInput.ts:1-6`; `treg.instagram.post.comments` takes `shortcode` or `url`). Only 1 of 1,134 execution calls (81 missions) used a `treg.*` endpoint (7.4); the engine calls direct provider endpoints.
- **NOT PROVEN:** that a failed or short delivery was caused by a missing second key (SQL keeps only `params_digest`, never the params).
- **Also:** `crawl4ai.instagram.user.posts` returns the 12 latest posts without a `session` and marks `meta.partial` for a larger limit (catalog summary): a request for 20 posts of an account can deliver 12.

### G13. Review limit
- **Requires:** review in batches until the requested count is reached or the ceiling is hit; no paid row dropped for a reason the customer cannot act on.
- **Today:** the review budget is 20% of revenue, the ceiling 40% of the reserve's value (`price.ts:147-154`, `constants.ts:212-214`); rows beyond it stay pending and are not delivered (`ingest.ts:239-241`); a stage whose last three pages bring nothing accepted while review has a stop ends with `review_limit` (`run.ts:30`, `:408-409`). The sentences: `finalize.ts:54`, `finalize.ts:175`, `methodology.ts:294` («بقي N دون مراجعة فلم يُسلَّم»).
- **Evidence:** 11 of 104 `result` events carry the review sentence (6 «بلغت حدّها المسموح»: `msn_6fe683c2…`, `msn_e750c243…`, `msn_24d0cf1d…`, `msn_82a287a5…`, `msn_51bd048e…`, `msn_d6437acc…`; 5 «تعذّر الوصول إليها»: `msn_9aa7fef9…`, `msn_f0211c1a…`, `msn_f86308d4…`, `msn_e91fd8b3…`, `msn_91475fe5…`). `msn_6fe683c2…` and `msn_e750c243…` delivered 5 companies and 0 people (`stage_2_rows 0`, charged 67).
- **Inconsistency found:** the review's own price table (`PLANNER_MODEL_PRICE` 0.10/0.50 per million) puts a review at about 0.000018 USD per row (`constants.ts:204-206`), so a budget of 0.07 USD or more (20% of the 200-point minimum charge) buys thousands of rows. Yet `msn_24d0cf1d…` (5 requested, 2 delivered) says the limit was reached with `execution_llm_usd` 0.0000. So either the stop is set by something other than money, or review spend is not recorded; the customer sentence may be wrong. NOT PROVEN which (`review_state` is in storage; admin page).
- **Size:** M. Diagnose first (log spent / budget / ceiling / worst per stop), then continue in batches to the ceiling, and price the review rows by the measured per-row cost.
